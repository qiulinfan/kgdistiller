# Parallel worker handoffs

Give each worker the immutable package path, source entrypoints, exact version,
user's actual reading request and language, and its output path. Do not invent a
learner profile. State that workers share the workspace, must write only owned
outputs, must not revert others' work, and must not modify source files.

## Translator

Use a fresh worker with this task:

> Use the transcription and translation stages of `$extract-paper-markdown` on
> the already prepared package at <package>. Read all original TeX and includes.
> You own only <package>/paper.md and <package>/paper_ch.md. Produce complete,
> corresponding full texts and run bilingual validation. Source acquisition has
> already passed preflight; do not redownload or change it. Other workers are
> using this package: do not edit their files or revert their changes. Return the
> two paths and any unresolved translation/source issue.

The translator owns both Markdown files so paragraph/block alignment does not
require synchronization with another writer. Preserve the user's explicit
translation preferences over the Skill defaults.

## Independent reader

Use the `paper-reader` preset or a fresh general-purpose worker. Supply only the
following natural reading request, source locations and ownership information:

> Read the paper at <source entrypoints and package path> and explain it to the
> user in <language>. The user's request is: <actual request>. Help them understand
> the author's ideas, terminology, method and reasoning as you normally would.
> Read the original source and relevant includes. Write your complete explanation
> to <package>/reading.md and return it to the parent. Do not use Skills or a
> personal knowledge graph for this task. Other workers share the workspace; you
> own only reading.md and must not edit source or other workers' files.

Do not prepend the orchestrator's Skill, the prior discussion of graph design, a
concept inventory, or a detailed explanation template. The reader independently
chooses the explanation structure and depth from the actual user request and
paper. It may look up necessary background without turning that into a graph
workflow. The parent verifies the result; the reader is not told which graph
nodes or review opinions it is expected to produce.

## Graph extractor

Use a fresh worker with this task:

> Use `$distill-paper-knowledge` to extract methods and mechanisms from the
> prepared source-only package at <package>. You own only <package>/knowledge/.
> Read original TeX now; paper.md and paper_ch.md are being generated by another
> worker and are not prerequisites. Produce the candidate, validated snapshot,
> paper-graph.md, and readable entries. Preserve paper-scoped identities. Query
> the established personal knowledge base through `$query-kgdistiller` by default.
> Trace actual operations and derivation steps to specific definitions, operators,
> inequalities or theorem versions; verify their conditions and link existing
> entries. Record where each dependency is used and why. An accurate, applicable
> existing match means the user has mastered that specific knowledge: link it and
> do not re-explain it. Explain only unmatched or non-equivalent parts. Never infer
> mastery of a broad subject from these matches. Other workers share the workspace: do not
> change their files or the source. Return the graph/entry paths and actual gaps.

Pass the established knowledge-project target or registered default to this
worker, respecting an explicit user opt-out. If no target can be resolved, continue
local extraction and report the linking branch as incomplete; do not fabricate
unmatched results or initialize a new vault. The graph lookup must not change or
gate the independent reader's explanation. Import requires a separate authorized
transaction.
